## Per-bullet findings

### A1 — validated user-level registry, closed shape, credential hygiene — MET

`~/.code-copilot-team/routing.toml` parsed by the constrained-TOML
parser in `scripts/lib/routing-config.sh`. `[policy]`,
`[route_classes.*]`, `[[profiles]]` accepted; every other table refused
by name (`routing-config.sh:103`). Dotted keys, inline tables,
multiline strings, literal strings, other arrays-of-tables, duplicate
tables and duplicate keys each carry their own named refusal
(`:90,:97,:119,:153-155`).

Credential hygiene is **structural**, as the bullet requires: no field
holds a literal credential — `credential_env` / `base_url_env` carry
environment-variable *names*, and nothing in the library reads those
variables' values (`:20-24`, `:57`). A defense-in-depth secret-shape
scan over every parsed string and array element
(`rc_secretish`, `:262-309`) rejects value-shaped secrets in any field.
The file states plainly that this scan is not complete secret
detection and that the structural boundary is the guarantee — an
accurate self-description, not an overclaim.

### A2 — vocabulary aligned with the benchmark harness backend contract — MET

`RC_BACKENDS="claude-code codex pi"` (`routing-config.sh:36`).
Benchmark harness families: `claude-code`
(`backends/claude_code.py:48`), `codex` (`backends/codex.py:46`), `pi`
(`backends/pi.py:41`) — exact string match on all three.

The harness additionally defines `aider` (`backends/aider.py:58`) and
`stub` (`backends/stub.py:21`), which routing refuses. This is correct
rather than divergent: `aider` is a measurement-only comparator backend
and `stub` a test double; neither is an execution harness the router
could route a build to. `plan.md:70-71` records the intended alignment.

Tiers (`tier1 tier2`), roles, data policies and quota pools are closed
lists in the same file (`:37-39`).

### A3 — trust-asymmetric `automation.json` routing block — MET, including the C/D promotions

Restriction-only enforcement is present in **both** layers:

- `scripts/validate-automation-config.sh:515-529` — closed key set;
  a repo attempting to *define* profiles gets a named refusal
  (`:523`), as does any attempt to introduce credential, endpoint,
  identity or capability fields (`:525`).
- `scripts/lib/routing-config.sh:502-512` — `rc_effective` re-checks
  the same top-level key set before composing.

The bullet says `tier2` / `recovery` are "refused by name until
increments C/D ship". **Both increments have shipped and both keys were
promoted correctly**, following the documented
refused→implemented→tested path:

| Key | Promoted by | Enforcement |
|---|---|---|
| `routing.tier2.delegation_enabled` | #254 T6 | `routing-config.sh:560-569`, `validate-automation-config.sh:544-562` |
| `routing.recovery.wake_enabled` | #257 D T3 | `routing-config.sh:571-579`, `validate-automation-config.sh:565-585` |
| `routing.recovery.auto_failback_enabled` | #257 D T3 | `routing-config.sh:580-583` |

Both promoted blocks are closed at the **sub-key** level too
(`validate-automation-config.sh:556`, `:580`), and both use the
explicit-null discipline so an explicit `false` cannot be widened back
to `true` by jq's `//` operator — the same hazard already handled for
`enabled` at `routing-config.sh:518-520`.

**Observation, not a defect:** `rc_effective`'s docstring claims it
re-checks "that the repo routing block carries ONLY the closed
restriction keys". That re-check is one level deep — it validates
top-level keys but not the `tier2.*` / `recovery.*` sub-keys, so a
typo such as `tier2.delegation_enable` would be silently ignored by
`rc_effective` alone. This is **not reachable in practice**: all three
consumers run `validate-automation-config.sh` first
(`routing-cli.sh:110`, `routing-cli.sh:757`,
`cooldown-supervisor.sh:372`), and that validator does refuse the typo
by name. The docstring slightly overstates the depth of its own
defense-in-depth; no code path is affected.

### A4 — normalized result contract + classifier proven against captured output — MET

`shared/schemas/routing-result.schema.json` freezes the nine-cause
taxonomy with `additionalProperties: false`. `failure_class` is
documented as CAUSE, never provider wording and never routing action;
`unknown` is the fail-closed residual.

`scripts/lib/routing-result.sh` implements an explicit precedence
ladder (structured envelope → specific semantic signals → generic
availability → `unknown`) with one named pattern per class, so a
weakened pattern is visible in `evidence.pattern` and a test can mutate
exactly one. The bullet's requirement that an HTTP status alone never
determine cause is enforced: every predicate requires affirmative text.

The captured corpus at `tests/test-routing-config.sh:243-266` pins 22
fixtures to exactly one class each, covering every category the bullet
names — usage limit (`claude-session-limit`, `claude-weekly-limit`),
429 (`api-429-structured`, `api-429-text`), 5xx
(`api-overloaded-structured`, `http-503-text`), transport
(`transport-refused`, `transport-dns`), auth (`api-auth-structured`,
`billing-text`), **context overflow** (`vllm-context-overflow`), test
failure (`exec-tests-failed`), and unmatched-novel (`novel-unmatched`).
Four ambiguity fixtures pin the fail-closed reading of a bare 403, and
`amb-dual-quota-rate` pins quota-before-rate precedence as intentional.
Evidence method and confidence are asserted separately (`:270-275`).

### A5 — `cct routing validate | status | explain`, read-only — MET (surface stale)

All three subcommands exist and dispatch through `scripts/cct:61-62`
to `scripts/routing-cli.sh` (`validate` `:221`, `status` `:251`,
`explain` `:293`). `explain` is a pure config-resolution dry run.
`status` renders `unknown` when no state file exists
(`routing-cli.sh:266`) and reads real circuit state via
`rs_effective_state` (`:127`) now that B/D write it — the bullet's
"unknown until B writes state" behaviour resolved correctly rather
than staying frozen.

**Finding (documentation, low severity):** `scripts/cct:27-30` still
advertises routing as *"#109 increment A — read-only"* and lists only
`validate`, `status`, and `explain --route-class`. Since increments
B–D, `routing-cli.sh` also ships `enable <profile-id>` and
`tick --due --once [--wake]` — both explicitly **impure** operator
actions — and `explain --feature <id> --task <id>`. `routing-cli.sh`'s
own usage text (verified by running it) is accurate and complete; only
the top-level `cct` help is stale. A user reading `cct help` is told
the routing surface is read-only when two of its commands mutate
state.

This is a stale help string, not a contract or behaviour gap. It does
not affect any code path and no test asserts the `cct` help content for
routing.

#### Resolution — fixed by the PR that lands this audit

`scripts/cct` now lists all five shipped routing subcommands and
separates them by purity, so a reader is no longer told the surface is
read-only:

```
  routing         Execution-profile routing (#109). Pure — read-only:
                    cct routing validate [--config <automation.json>]
                    cct routing status
                    cct routing explain --route-class <class> [--role <role>]
                    cct routing explain --feature <id> --task <id>
                  Impure — these mutate routing state:
                    cct routing enable <profile-id>
                    cct routing tick --due --once [--wake]
```

The absent-coverage half of the finding is closed too. One assertion
was added to increment A's own suite
(`tests/test-routing-config.sh`, beside the existing `cct` front-door
dispatch check) pinning every shipped subcommand name, the
task-addressed `explain` form, the presence of the impure label, and
the absence of the stale "increment A — read-only" claim.

The assertion was **mutation-tested five ways** rather than trusted for
passing on the first run. Each mutation to `scripts/cct` was applied
in isolation and the suite re-run; every one produced
`167 passed, 1 failed`:

| Mutation | Result |
|---|---|
| drop the `tick` line | fails ✓ |
| drop the `enable` line | fails ✓ |
| drop the task-addressed `explain` line | fails ✓ |
| restore the stale "increment A — read-only" claim | fails ✓ |
| replace the "Impure" label with "Also:" | fails ✓ |

Counts after the fix: `test-routing-config.sh` **168 passed, 0
failed**; `tests/test-counts.env` pin raised 167 → 168, and the
mirrored count in `README.md`'s file tree raised to match (the two
are enforced to agree by `test-shared-structure.sh`, which passes at
812). `check-doc-accuracy.sh` clean.

## Not demonstrated

These limitations describe the audit itself and are **not** retracted
by the A5 fix — that fix corrected a help string and added one
assertion; it did not widen what this audit verified.

- No live backend was invoked. This audit reads code and runs the
  existing suites; it does not re-verify any recorded live capture.
- `test-auto-build-loop.sh` and `test-cooldown-supervisor.sh` were
  **not** run: the audit changed no code, and the A5 fix touches
  neither. (`test-shared-structure.sh` and `check-doc-accuracy.sh`
  *were* run for the fix, since it changes a count `README.md`
  mirrors — 812/0 and clean respectively.)
- Coverage of the `cct` help text **was** absent by construction: no
  test asserted it, which is why the A5 staleness went unnoticed. That
  specific gap is now closed. No other `cct` help section — `list`,
  `doctor`, `config` — has any coverage, and this PR did not add any.

## Recommendation

**#248 is closable on its own scope.** Every scope bullet is met, the
two keys it deferred to C/D were promoted correctly when those
increments landed, and the classifier corpus proves what the bullet
claims it proves.

The one finding — the stale `scripts/cct` routing help — was a defect
against #248's A5 surface but not against A5's behaviour, and it
equally reflected B/C/D extending the surface without updating the
top-level help. **It is fixed in the PR that lands this audit**, with a
mutation-tested regression assertion, so #248 can be closed without
knowingly leaving its user-facing command surface inaccurate.

Closing #248 leaves #109 open (umbrella).
