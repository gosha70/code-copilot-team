## What was put to the owner

The S4 capture against Claude Code 2.1.332
(`verification/claude-code-session-capture.md`): `--session-id` names a
new session, `--resume <id>` keeps it, an id already in use is refused,

## The owner's rulings

The owner's message of 2026-11-25, quoted in full:

> The main decision I’d make from this update is on the new Claude Code environment variables: do not add any of them to CCT’s clear-list yet.
> The capture against Claude Code 2.1.332 already establishes the important S4 behavior: explicit `--session-id` creates the named session, `--resume <id>` preserves it, reuse of an active ID is rejected, and bare `--continue` follows the most recently used session—which supports FR-18’s refusal of `--continue` under `--llm`.
> For these newly observed names:
>
> * `CLAUDE_CODE_MODEL_NOBODY_CHOSE`
> * `CLAUDE_CODE_SENDS_VIA_SESSION_SERVICE`
> * the two `…_CHECK_PROVIDERS` names
>
> I agree with the current conservative choice. Their presence in the binary does not establish that they affect model selection or routing, and clearing undocumented Claude-internal variables would itself become behavior CCT owns. The capture explicitly says there are 30 new names since 2.1.329 and that these particular names only might affect model/route selection.
> For S4, I would encode the owner ruling as:
> D-S4-env: CCT clears only environment variables for which executable evidence demonstrates that inherited state can override or alter the CCT-selected LLM target. Newly discovered Claude Code variables remain untouched until their semantics are demonstrated. Variable names or binary-string presence alone are not sufficient evidence.
> That gives you an evidence-based rule rather than having to revisit each Claude release ad hoc.
> The rest of the S4 direction also looks right. CCT should own the session identity explicitly rather than relying on cmux: generate the UUID, stamp the attempted launch before executing Claude, and pass `--session-id` itself. The cmux wrapper already avoids injecting a second ID when one of the relevant session flags is present, so there is no reason to make wrapper behavior authoritative.
> For resume, I would make the contract strict:
>
> 1. `--llm ...` + bare `--continue` → refuse.
> 2. `--llm ...` + resume-picker behavior → refuse.
> 3. Explicit `--resume <session-id>` → look up the CCT stamp first.
> 4. Re-resolve the requested target from current config/compatibility.
> 5. If the stamped original target and newly resolved target differ → refuse, naming both.
> 6. If they agree → invoke Claude with the exact session ID and target.
> 7. `cct llm sessions` should expose at least session ID, harness, target/model, stamp state, project, and whether resume is eligible.
>
> That matches the plan notes quoted in the update: S4 owns “stamps and exact-id resume,” refuses `--continue` and the picker under `--llm`, and refuses resume under a different target.
> On #535, I would make no code change for the CodeQL result described here. The follow-up regression is well supported: all 231 failover tests pass on the branch, the new race test fails specifically against `b397714`, and the routing suites are clean. The later CodeQL failures occurred during result upload while GitHub was returning 502/500 errors, whereas sync-check and Pi tests were green. Pasted text Once GitHub is healthy, a clean CodeQL rerun is sufficient evidence; I would not modify the PR to appease an infrastructure failure.
> So my ruling is: leave the new Claude variables alone and proceed with the S4 launcher/resume implementation under an explicit evidence-before-clearing rule.

## The three choices S4 made, and the owner's acceptance

Where the rulings are silent, S4 made three choices and put them to the
owner, each recorded in `spec.md`:

1. A `--session-id` given with `--llm` is refused, read from the
   identity ruling: an id the user picks could name an existing session,
   whose stamp would be replaced before Claude Code refused the id (D9's
   note).
2. A resume by exact id with `--llm` and no stamp is refused: the
   target the session was started with is unknown (FR-18's note).
3. The native notice for a bare `--continue` or the picker prints only
   where stamps exist, so a launcher that never used `--llm` stays as it
   was (FR-18, an S4 departure).

The owner's reply of 2026-11-25, after #535 merged, quoted from its S4
part on:

> S4: I accept all three choices. (1) Refuse --session-id with --llm, saying to drop it. (2) Refuse resuming an unstamped session by id with --llm, naming resume-without---llm and --fork-session as the ways out. (3) The native note only where stamps exist, with the departure from FR-18 recorded in the spec. In the PR body, please: cite where #399 pinned 2.1.305 or put it to me as a new choice; say whether launches now consult the minimum version and what the rule-version bump does to existing records; and list the 30 new Claude Code variables, each with why it stays off the clear-list.

The refusal of (1) says "Drop --session-id"; the refusal of (2) names
`--resume <id>` without `--llm` and `--resume <id> --fork-session --llm
<target>`; (3) is FR-18's dated departure. The PR body answers the three
requests about 2.1.305, the minimum version and the records, and the 30
