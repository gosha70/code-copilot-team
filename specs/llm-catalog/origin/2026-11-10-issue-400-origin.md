# Origin record — harness-agnostic LLM catalog and `--llm` selection (#400)

Recorded 2026-11-10 from the issue text, the repository at `42f5883`
(origin/master after PR #443), and the four external references the
issue cites, each read on this date. Quotations are the owner's words;
everything else is a fact observed in the tree or on the cited page.

## Issue origin

Issue: https://github.com/gosha70/code-copilot-team/issues/400
(opened 2026-11-02 by the owner, label `enhancement`, no comments).

The problem, in the issue's words:

> Code Copilot Team has several ways to describe models and providers,
> but no single user-facing way to configure named LLM targets and
> choose one when starting an AI harness.

> The desired workflow is to configure multiple named LLM targets
> once—similar to RLM Studio's provider setup—and optionally select one
> when starting a harness. If no target is selected, the harness must
> retain its native configured behavior.

The product promise the issue sets:

> The product promise must be **any configured LLM target on any
> compatible harness**, not "any LLM on any harness."

The six parts of the proposed solution: (1) a normalized user-level
catalog at `~/.code-copilot-team/llms.toml` with **providers**,
**endpoints**, **llms** and **bindings**, credentials as references
only; (2) `--llm` as the common per-launch selector, never `--profile`;
(3) harness-specific launch adapters that resolve a catalog entry into
an inspectable `LaunchPlan` (executable and arguments, child-only
environment, temporary or layered config overlay, redacted identity,
compatibility evidence, cleanup ownership), with commands in cmux/tmux,
shell history and logs carrying stable IDs only; (4) an explicit
compatibility state per `(harness, llm)` pair — `supported`,
`unsupported`, `unverified`, `unavailable`, `incompatible` — decided
before launch, with a falsifiable behavioral probe ("A successful
`/models` request alone is not sufficient"); (5) session and resume
semantics with a redacted provenance stamp; (6) reuse of the routing
registry, the routing config library, the supervisor and the two
launchers "without preserving its coupling".

The delivery plan names seven increments A–G (catalog and read-only
CLI; Claude Code; Codex; Pi; Kiro; unified launch and Studio UI;
routing/provenance migration) and ten acceptance criteria, quoted in
`spec.md` § Success Criteria.

## Repository facts the issue builds on (observed at 42f5883)

- `adapters/claude-code/claude-code` (1,860 lines) builds the launch
  string with `build_launch_command` and types it into cmux
  (`cmux send`) or tmux (`tmux new-session … "$run_cmd"`); inside a
  multiplexer it execs `claude` directly. Unknown `--flags` are
  forwarded verbatim to `claude`. Its `gateway_compat_notice` (PR
  #425, #399) prints when `ANTHROPIC_BASE_URL` is set and no
  tool-compatibility variable is, and its comment states: "Applying the
  variables belongs to an explicit per-launch selector (#400)."
- `adapters/pi/bin/pi-code` (713 lines) forwards unknown options to
  `pi` and execs `pi --extension <runtime>`; its child-session runtime
  already passes `--model` per agent.
- There is no Codex launcher and no Kiro adapter in the tree; the only
  Kiro mentions are Session Analytics harness names.
- `shared/templates/routing/routing.toml.example` and
  `scripts/lib/routing-config.sh` (688 lines, bash 3.2, constrained
  TOML grammar, credentials as `credential_env` / `credential_mode`
  names, `base_url` / `base_url_env`, a `protocol` field, and a
  defense-in-depth secret scan). `scripts/cooldown-supervisor.sh`
  wires `ANTHROPIC_BASE_URL` and `ANTHROPIC_API_KEY` into the child
  environment only (`rt_launch_env`), passes `--model` and
  `-c model_provider=<id>` to `codex exec` (verified against codex-cli
  0.147.0 per its comment), scrubs the wired secret from every capture,
  and records Codex's effective endpoint as `none` because the user
  config file is one layer of Codex's configuration.
- `scripts/lib/routing-probe.sh` already defines the probe contract the
  issue asks for: "a SMALL REAL INFERENCE through the profile's own
  backend plus … a MINIMAL TOOL-CALL CANARY. `/v1/models`, `--version`,
  and a TCP connect are insufficient BY CONTRACT".
- `shared/scripts/provider-emit.sh` with `~/.code-copilot-team/
  providers.toml` (the reviewer profile) emits per-copilot config
  snippets at setup time (spec `specs/provider-config`); it is a
  setup-time emitter, not a per-launch selector.
- `scripts/cct` dispatches `start` to the installed `claude-code`
  launcher, `routing` to `scripts/routing-cli.sh`, `doctor` and
  `config` to Python helpers.
- Issue #411 (open) is deciding whether `~/.cct/` or
  `~/.code-copilot-team/` is the one harness home; the catalog path
  must resolve through one helper so that migration moves it.

## External facts read on 2026-11-10

- **Claude Code** (code.claude.com, llm-gateway-connect, model-config,
  cli-reference): `ANTHROPIC_BASE_URL` points at a gateway; the
  credential is `ANTHROPIC_AUTH_TOKEN` (bearer) or `ANTHROPIC_API_KEY`
  (`x-api-key`); `ANTHROPIC_CUSTOM_HEADERS` adds headers. Model
  priority: `/model`, then `--model`, then `ANTHROPIC_MODEL`, then the
  settings `model` field, then `ANTHROPIC_DEFAULT_MODEL`;
  `ANTHROPIC_DEFAULT_{OPUS,SONNET,HAIKU}_MODEL` set what the aliases
  resolve to, not the session model. "`ANTHROPIC_BASE_URL` changes
  where requests are sent, not which model answers them." Resumed
  sessions "keep the model they were using when the transcript was
  saved"; `--session-id` accepts a UUID. `CLAUDE_CODE_DISABLE_
  EXPERIMENTAL_BETAS=1` "suppresses most pre-release fields".
- **Pi** (earendil-works/pi docs: models, models-configuration, cli,
  sessions): custom providers live in `<agent-dir>/models.json`
  (default `~/.pi/agent`); provider fields include `baseUrl`, `api`
  (`openai-completions`, `openai-responses`, `anthropic-messages`, …),
  `apiKey` with `$NAME` / `${NAME}` environment interpolation and
  `!command` forms; `--provider <name>` "requires `--model`";
  `PI_CODING_AGENT_DIR` moves the whole agent directory; "A session
  records model and thinking-level changes. Resuming the session
  restores them"; `--session <path|id>`, `--session-id <id>`,
  `--fork` exist. Not found: whether an unknown provider is refused
  before start.
- **Kiro** (kiro.dev/docs/models, docs/cli/headless): executable
  `kiro-cli`; "Pass `--model <id>` to pin the model for a run"; the
  model list is Kiro-managed; no custom endpoint, base URL or
  bring-your-own-key surface was found; headless needs
  `--no-interactive` and `KIRO_API_KEY`; `--resume-id <ID>` resumes;
  "Without `--model`, a resumed session keeps its original agent and
  model."
- **Codex** (the config reference now served from
  learn.chatgpt.com/docs/config-file/config-reference): the
  `[model_providers.<id>]` table has `name`, `base_url`, `env_key`,
  `wire_api`, `http_headers`, `env_http_headers`, `query_params`,
  retry/timeout keys; the page read lists only `responses` for
  `wire_api` and documents `--profile` as layering
  `$CODEX_HOME/<name>.config.toml`. The CLI precedence among flags,
  `-c` overrides, profiles and files, and `codex resume`, were not on
  the page read. The repository's own capture against codex-cli
  0.147.0 (`cooldown-supervisor.sh`, `codex-reviewer-capture.md`)
  established `-c key=value`, `-p/--profile` layering and
  `--ignore-user-config`. The Codex adapter re-verifies these against
  the installed CLI as its first task.
- **RLM Studio** provider UX (github.com/gosha70/rlm-studio) is cited
  as inspiration for the configure-once workflow; it was not read for
  this record.
