## What was put to the owner

On 2026-11-23 the owner asked for S3's consequence to be stated in full
and for a milder rule to be put to them as an open decision for S3
(`2026-11-23-replan-rulings.md`, ruling (3)). `plan.md` records it as
open decision 1. Two questions were put on 2026-11-26.

1. **The rule S3 builds.** The question said that, as ruled, the
   evidence digest includes Claude Code's version, and that Claude Code
   went from 2.1.329 to 2.1.332 in about a week, so every update would
   return every target to unverified. The options were:
   - "Milder rule": "Refuse a target that was never tested, whose
     latest conclusive test failed, or whose launch identity changed.
     When only Claude Code's version is newer than the passing test's,
     print a notice and launch. Amends FR-12, FR-13 and D7. Without it,
     near-daily updates would push people to --allow-unverified."
   - "Strict D7, as ruled": "Every Claude Code update refuses every
     target until `cct llm test` passes again on the new version;
     `--allow-unverified` is the only way past it."
2. **Under the milder rule, a changed tuning option or an older rule
   version.** A target whose options digest changed (for example
   `small_fast_model` or `auto_compact_window`), or whose passing test
   was recorded under an older CCT rule version. The options were:
   both refuse; both get the notice; a changed option gets the notice
   and an older rule version refuses.

## The owner's rulings

For (1) the owner chose "Milder rule", and for (2) "Both refuse", the
two options the session had marked as its recommendation. The text of
"Both refuse":

> Only a newer Claude Code version gets the notice. A changed option is
> the user's own edit, and a newer rule asks for evidence the old test
> lacks, so both read as unverified until `cct llm test` passes. Today's
> S2 code already reads an older rule version as unverified.

## What the rulings change

- **Only a newer harness version is let through.** A target whose
  latest conclusive record passed, and whose evidence matches that
  record in everything but the harness version, launches with a notice
  when the installed harness is newer than the record's. The notice
  names both versions and the command that tests the target again.
- **Everything else in the evidence digest still refuses.** A target
  never tested, one whose latest conclusive record failed, one whose
  launch identity changed, one whose options digest changed, and one
  whose record predates the current rule version are refused, as D7
  ruled. So is a harness older than the record's, which the ruling does
  not let through.
- FR-12, FR-13 and D7 carry the amendment, dated 2026-11-26, in
  `spec.md`; `plan.md` marks open decision 1 settled.

## 2026-11-27: the owner's second review of #547, and a ruling

The owner's reviewer ran the real Claude Code 2.1.332 against `ed20a64`
and reproduced the session's caveat: with a user rule that allows all of
Bash, the endpoint's appended command ran and the test passed. The
owner asked, in the reply for the builder:

> (1) Fail `tool_call` when the endpoint asks Bash for anything other
> than `sh canary.sh`, as you proposed. Also try to prevent the run:
> pass `--settings` with a PreToolUse hook on Bash that blocks any other
> command, and test it against a user settings file that allows all of
> Bash. If the hook doesn't hold, warn before the run when the user's
> settings allow Bash broadly.
> (2) Add `--tools Bash` so the endpoint isn't offered the other tools.
> (3) `model_identity`: with `unverifiable`, an alias target can never
> become `supported`. I'll send the managed and API outputs; if names
> differ, record the reported name on the first pass and compare later
> runs with it.

The session found that `--tools Bash` cuts the request to two tools
(Bash and a tool-search placeholder) from the twelve a headless session
offers, so an endpoint that rejects another tool's schema would pass
the test and fail every launch; and that the hook, matching every tool,
held against `allow: ["Bash"]`, `defaultMode: bypassPermissions` and an
approving user hook, and only `disableAllHooks: true` turned it off. It
asked the owner whether the test should still offer every built-in
tool. The owner chose "Keep all tools (Recommended)":

> The test's request matches a launch's. The guard hook blocks every
> call except the canary's command. With hooks disabled, the warning and
> the failing verdict still apply.

What this changes: both runs get the hook; any tool call the endpoint
asks for other than the canary's command fails `tool_call`, refused or
not; the warning names a settings file that sets `disableAllHooks`; no
`--tools` flag is passed. (3) waits on the owner's two runs.

### 2026-11-27, later: refuse when hooks are off

At `1e27311`, the owner wrote:

> One item from the last review is still open at 1e27311: when
> lp_hooks_off finds hooks off, the test warns and runs, and the
> endpoint's own command then executes (the reviewer reproduced it with
> the real Claude Code). Make it refuse and name the cause, with a flag
> such as --without-guard to proceed, and add a test.

What this changes: when hooks are off for the test, `cct llm test`
refuses before anything runs (exit 3), naming the cause and
`--without-guard`; with that flag it runs unguarded, warned of first.
The flag never turns the guard off where hooks are on.
